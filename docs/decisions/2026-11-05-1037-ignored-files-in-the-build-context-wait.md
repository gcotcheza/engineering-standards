# Ignored files in the build context wait for their own card

Card 363 asked two things of the root compose path: that a build runs only over the merge commit, and that no file the app user can add reaches the build context. The first is now `deploy_compose_tracked`: as the app user, `git status --untracked-files=no` must be empty and `rev-parse HEAD` must be the sha fleet-deploy exported (`<run>/export-sha`, which `deploy_compose_init` already proved is the merge), so a tree reset to another clean commit is refused, naming both shas.

The second is not done here, on purpose. Refusing a tree where `git status --porcelain --ignored` lists anything under a path a Dockerfile COPYs is not cheap and would not be right. Every app's build context is its tree's root or a `docker/` directory, and every deployed tree holds ignored files by design: `.env`, `vendor/`, `node_modules/`, `storage/`, `public/build`. A blanket refusal stops every deploy. A narrow one has to know which of those files actually enter the context, which means parsing each Dockerfile's `COPY`/`ADD` sources (globs, `--from` stages, heredocs, `ARG`-built paths) and applying `.dockerignore` with Docker's own matching rules; a shell copy of those rules that drifts from Docker's reads as safe while it is not, which is worse than the known gap (C9).

What already holds: `deploy_compose_buildcheck` refuses any file under `docker/` that is not in the merged commit, and every Dockerfile and `.dockerignore` must match the export byte for byte. What remains open: an ignored or untracked file elsewhere in a context that `.dockerignore` does not exclude can reach the image. The sound fix is to build from the exported commit itself (a `git archive` of the merge as the context, which is what fleet-deploy already does for `compose/` and `buildcheck/`), not to inspect the live tree; that is a fleet-deploy change and goes on its own card.
