# Why gate-image-tags reads no arrays among compose options

`scripts/gate-image-tags.sh` takes the first non-option word after `docker compose` as the call's subcommand. When that word is a quoted array word such as `"${A[@]}"`, the `-f` values after it are never read, the call is judged on compose's default file set, and over a default pair holding a production tag the check goes red (memento's false red, worked around in memento as 75029c91). That red stays: the check now only says why, naming the file and line of the call and pointing here.

Card 1112 tried five rounds to read such arrays through their assignments instead, and each adversarial review found new ways around the reading: round 1 d1c61be, round 2 05a4fe2, round 3 b2489cb with its case 20e2aa2, round 4 d12334a with round 5's cases 91a4b09 (reviews in `/srv/worker-scratch/1112-rev`, `-rev2`, `-rev3`, `-rev4`). Round 4 alone was shown 13 bypasses, among them option words glued to or quoted with their values, `trap`, `alias` and `mapfile -C` writes, arithmetic writes and a name hidden as `$'\101'`, plus new false reds. An array's content is whatever bash ran to build it, and a regex reader that follows part of bash passes files it never saw; a guard that refuses what it cannot read is tighter than one that reads some of it. So the approach was abandoned (advisor ruling 2026-11-14), and the round branch in `/srv/worker-scratch/1112-es` was never pushed.

The message never prints the array's value or any variable's content (S2); only the call's location and the tag it reaches. The bare form `${A[@]}`, which the tokenizer splits into pieces, keeps the generic message; exit status and every other path are unchanged.
