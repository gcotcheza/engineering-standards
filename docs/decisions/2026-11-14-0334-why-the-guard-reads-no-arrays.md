# Why gate-image-tags reads no arrays among compose options

`scripts/gate-image-tags.sh` takes the first non-option word after `docker compose` as the call's subcommand. When that word is a quoted array word such as `"${A[@]}"`, the `-f` values after it are never read, the call is judged on compose's default file set, and over a default pair holding a production tag the check goes red (memento's false red, worked around in memento as 75029c91). That red stays: the check now only says why, naming the file and line of the call and pointing here.

Card 1112 tried five rounds to read such arrays through their assignments instead, and each adversarial review found new ways around the reading: round 1 d1c61be, round 2 05a4fe2, round 3 b2489cb with its case 20e2aa2, round 4 d12334a with round 5's cases 91a4b09 (reviews in `/srv/worker-scratch/1112-rev`, `-rev2`, `-rev3`, `-rev4`). Round 4 alone was shown 13 bypasses, among them option words glued to or quoted with their values, `trap`, `alias` and `mapfile -C` writes, arithmetic writes and a name hidden as `$'\101'`, plus new false reds. An array's content is whatever bash ran to build it, and a regex reader that follows part of bash passes files it never saw, so the guard does not try. So the approach was abandoned (advisor ruling 2026-11-14), and the round branch in `/srv/worker-scratch/1112-es` was never pushed.

Refusing beats reading. The gap this left is closed: main exited 0 for `A=(-f docker-compose.yml)` then `docker compose -f docker-compose.ci.yml "${A[@]}" build app`, because the array word after a gate -f was taken as the subcommand and never judged. Now every array expansion among the options after a read `-f` is red, with its own FAIL line naming the file and line and an "unread array word(s)" trailer. An array expansion is any option word holding `${`, an optional `!` or `#`, then `NAME[@]` or `NAME[*]`, quoted or bare, with any operator, prefix or suffix: `"${A[@]}"`, `${A[*]}`, `"${A[@]:-}"`, `"${!A[@]}"`, `"x${A[@]}"`, `"--env-file=${A[@]}"`. The value word an option such as `-p`, `--profile`, `--env-file` or `--ansi` takes is an option word too, so `--profile "${A[@]}"` is red: bash hands compose every element, and the ones after the first are options again. That holds for harmless content too, such as `(--env-file /dev/null)`, because telling harmless from harmful means reading the array. The call is still judged on what was read, so every earlier finding stands. A whole-command array (`"${COMPOSE[@]}" build`) is read as before, and an array after the subcommand is not an option. Not covered: a word-split scalar such as `$X` holding `-f …`, and a call whose files come from `COMPOSE_FILE` with no `-f`, where an array word still stands as the subcommand.

Merge order: memento PR #215's gate calls `-f … -f … "${GATE_ENV_FILE[@]}"`, which this turns red, so this change merges only after memento card 1114 is live and takes the array out of those compose options (advisor ruling 2026-11-14 03:56Z); #215 itself is not held.

The message never prints the array's value or any variable's content (S2); only the call's location and the tag it reaches. The default-fallback line appears only when the run fell back to compose's default files; a run whose -f before the array word is the cause keeps the generic message beside the new array line.
