# The deploy lib leaves Laravel's cached config owner-only after every config:cache

`bootstrap/cache/config.php` holds APP_KEY and every database password in plain PHP. On 2026-11-19 it was 644 or 755 in all five Laravel apps on prod (card 1031, S8). `php artisan config:cache` writes it again on every deploy, and deploys now run on merge.

Not every app caches its config: Orbit's and health-tracker's deploys never run `config:cache`. The apps that do run it, or `optimize` (which runs it), through `$COMPOSE`, the lib's `compose.sh run`. So `deploy_compose_exec` reads its own arguments after a compose call succeeds. When `artisan` is followed by a `config:cache` command, or by `optimize` without `--except` naming `config`, it calls `config_cache_private` on the app root. The arguments are also split into words, so `sh -c "php artisan config:cache"` (kidsquest's e2e shape) and `bash -c` count; the command name is matched in any case, and only the first word after `artisan` (options aside) is the command, so `tinker --execute optimize` does not count. Symfony's abbreviations (`conf:cac`) are not parsed, because guessing them would refuse calls that cache nothing.

A miss is loud: after every other successful compose call, of any app, the lib runs `config_cache_check`, and when a cached config there is not owner-only it says so in a NOTE and runs `config_cache_private`. So an abbreviation, an entrypoint that caches, or a stale 644 file left from a hand run is repaired by that call or the next one, loudly (a cache an entrypoint writes after the deploy's last compose call waits for the next deploy), and Orbit's or health-tracker's stray cache is repaired whenever its deploy makes a compose call through the lib. fleet-deploy exports every flat file under `scripts/lib/deploy/`, so `config-cache.sh` reaches the run dir with no export change (pv proved this on prod's live run dir, 2026-11-19).

`config_cache_private` makes the file 0600 and then runs the check, so a chmod that did nothing still fails the deploy. Loud is right here (C9). A cache that root owns is refused: config:cache ran as root, and the fix is in the writer. A missing cache after config:cache is refused too.

As root, the chmod runs through `setpriv` as the numeric uid and gid that own the app tree, read from the tree after it is vetted as its own real path, and the cache must have that same owner. The app user owns `bootstrap/` and can swap `bootstrap/cache` for a link at any moment, so nothing below the tree is trusted for whose authority the chmod uses. The first version read the uid from the cache file by path; review r1 reproduced a swap in that gap that turned another uid's file to 600 as that uid. Now a swap reaches only files the app user could chmod already. This rests on the app user being unable to swap the tree itself, which holds where its parent belongs to root (`/var/www`); the lib does not check the parent. Acting on one file descriptor opened once was rejected: bash cannot open without following a link, and opening a swapped-in FIFO would hang the deploy. `setpriv` takes numbers, because the owner is a container uid that may have no name on the host. pv confirmed on prod that the cache's owner uid is the PHP-FPM worker uid in all five apps, so 0600 keeps the site readable to PHP.

Because the check also runs after every compose call, a cache whose owner differs from the tree's fails every compose call of that deploy, loudly. On prod on 2026-11-19 (advisor, read-only `stat`) no deploy hits this: the tree and cache uids match in the five apps that cache (fineprint 116, ghie-writes 996, ghiecode 999, kidsquest 114, moneywise 985), and the rest have no cached config. Scribly and reflection are Symfony apps with no host `bootstrap/cache` and no artisan, though their PHP runs as 82 and www-data, not the tree uid. If an app like that ever starts caching, the fix is to take the allowed uid from root's side (its `/etc/fleet/app-env/<app>.env`) or to chmod through an `O_NOFOLLOW` descriptor with `fchmod` in a helper, not to loosen the owner check. The tree-uid argument also assumes `/var/www` is owned by root and not group-writable; the lib records this and does not check it. The app user can now make its own deploys fail by planting a link as the cache, which is loud and the same class as a broken buildcheck.

`config_cache_check` is the VERIFY. A deploy or a health row can call it directly, or run `config-cache.sh <app-dir>` as a script. It passes when there is no cached config.

Rejected: a umask of 077 around config:cache. The lib cannot set the umask of a process inside `docker compose exec` or `run` without rewriting the app's command. The chmod straight after the call is what this change guarantees. An app may still wrap its own call in `umask 077` to close the moment between the write and the chmod. A hand-run `artisan config:cache` outside a deploy writes 0644 again, and the next deploy closes it.
