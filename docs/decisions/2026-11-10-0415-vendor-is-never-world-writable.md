# A composer vendor/ is never world-writable, and no image stage leaves busybox unzip behind an apk change

Card 797 found composer extracting packages with busybox `unzip`, which keeps the modes stored in a zip, so package directories came out 0777: any uid on the box could replace a package's code before the app ran it. Measured 2026-11-10, GhieCode had 1543 of 1585 vendor/ directories world-writable and Ghie Writes 1456 of 1501. The apps fixed it by building PHP's zip extension (composer then extracts with ZipArchive) and deleting `/usr/bin/unzip` from the image. 797 then found a second trap: any later `apk add`, `del`, `upgrade` or `fix` runs busybox's trigger, which relinks `/usr/bin/unzip`, so a gate stage that adds a package after the removal brings unzip, and the 0777 modes, back.

797 put the checks into four apps (GhieCode, Ghie Writes, Reflection, Scribly) as separate copies, and Orbit had none, five copies of one rule (C1). Card 1014 moves them here, as two scripts an app reads by literal path from `/srv/engineering-standards/scripts/`, the way it reads `decisions-check.sh`. The apps swap to them in their own pull requests.

`scripts/vendor-perms-check.sh <vendor-dir>` is the outcome check and fails closed: it passes only on `0 of N` with N above 1. It judges vendor/ itself as well as every file and directory under it (no `-mindepth`; 797's review measured a 0777 vendor/ passing as `0 of 3` with it), skips symlinks (their mode is always 0777), and refuses a symlinked vendor/, a vendor/ with no `autoload.php`, a `find` that fails on either of its two runs (an unreadable directory could hide a writable one), and a tree with nothing under vendor/ to judge. It is POSIX sh because apps run it inside their Alpine image's busybox ash as well as under bash; its test runs every case under both, except the failing-`find` case, which runs under dash because busybox sh calls its own find applet whatever PATH holds.

`scripts/dockerfile-unzip-check.sh [--stages N] <Dockerfile>` is the cause check. It joins `\` continuation lines first, dropping comment lines inside them as Docker does, so `apk \` with its verb on the next line is a change and a continuation that begins `from ` is no stage. Every other `FROM` starts a stage, so a child stage such as `FROM gate AS e2e` is judged alone; in each stage with an apk change, a removal of `/usr/bin/unzip` must come after the last change, and the check names each stage that leaves unzip. A removal counts only when it runs: `rm`, `rm -f` or `rm -rf` of exactly that path, at the start of a RUN or right after `&&` or `;`, before any ` #`. So `echo rm …`, a comment, `|| rm …` and `rm /usr/bin/unzip.bak` remove nothing, and neither does an rm in a RUN heredoc's body, while an apk change there still counts, so such a stage fails. GhieCode's reviewed copy accepted only the exact line `RUN rm -f /usr/bin/unzip && ! command -v unzip`; this check accepts any of those removal forms at those positions, and the in-image refusal below still catches one that leaves unzip behind. A Dockerfile in which no stage changes apk packages fails, because nothing was judged; `--stages N` also fails unless exactly N stages were judged, the pin both reviewed per-app copies carried, so an app keeps it when a rewrite of its Dockerfile slips past the regex. It reads the text, so it does not see apk behind a variable (`${APK} add`); the vendor check is the backstop for what it misses.

Neither script replaces an app's own in-image refusal, such as GhieCode's gate step `command -v unzip >/dev/null && die …`, which judges the built image rather than its Dockerfile. Apps keep that line when they swap their vendor block for these scripts.

Both tests run in gate step 2, right after `bash -n`: measured 2026-11-10, the pair took 2.18s and 2.65s against 2.88s and 2.83s for `fleet-budget-test.sh`, the cheapest step after it, and 63s for the tree-judging step that used to be second.
