# Root's compose allows build.provenance only when it is false

The root compose policy lets a service's `build` carry `args`, `context` and `dockerfile`, and now `provenance`, but only when it says false; any other value (`true`, `"true"`, `"False"`, `"mode=max"`, `"max"`, `"0"`, `""`, `null`) is refused by its own F rule, named by key and never by value.

What compose renders: compose-go (v2.16.1, in this box's docker compose v5.6.1) types `build.provenance` as a string and registers `transformStringOrX` for it, which turns a non-string through `fmt.Sprint`. So YAML `provenance: false` reaches the policy as the JSON string `"false"`, not the boolean. The rule accepts exactly that string and the boolean `false` (in case a later compose stops normalising); a rule that took only the boolean would refuse the very deploy it was written to allow.

Why false is wanted: BuildKit attaches a provenance attestation to the image by default, and the attestation records the build's time and invocation, so two builds of identical sources produce two different image ids, and `up -d` keeps the old container (GW card 809); a deploy then cannot prove that the running container is the image built from the merge. With `provenance: false` an identical build gives an identical id, which is what lets a deploy bind its running container to the merged build (T9's second half, GW card 809).

Why only false: provenance is the one `build` key that turns on extra work inside the builder, and its non-false forms (`mode=max` in particular) record build arguments and context details into an attestation stored with the image. Allowing the key in general would widen what an app's compose file can make root's build do; allowing the value that switches the feature off widens nothing. The match is exact: `"False"`, `"0"` and an empty string are refused, so no parser's idea of truthiness decides it.
